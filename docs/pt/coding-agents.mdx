Um agente de código como Claude Code, Codex ou Cursor pode escrever, rodar e
depurar testes e2e. Ele aprende o e2e pela skill, usa o app pelo servidor
`e2e mcp` e lê a página de trace de um teste que falhou.

## Instale a skill

<CodeGroup>
```bash npm
npx e2e init
```

```bash pnpm
pnpm dlx e2e init
```

```bash bun
bunx e2e init
```
</CodeGroup>

| Caminho | Usado por |
| --- | --- |
| `.agents/skills/e2e/` | Codex, Cursor, OpenCode e outros agentes que leem `.agents/skills` |
| `.claude/skills/e2e/` | Claude Code. Um link simbólico para `.agents/skills/e2e/` quando os dois estão instalados. |

O `init` coloca o `SKILL.md` e as referências por tópico nessas pastas, e o
[`e2e upgrade`](/reference/cli#e2e-upgrade) os mantém atualizados. Sem o
`init`, instale a skill com `npx skills add e2e-inc/e2e` ou imprima a skill a
partir do pacote instalado com `npx e2e guide [topic]`. O plugin abaixo instala
as três skills do e2e globalmente, para todos os projetos.

O `init` também adiciona uma indicação curta ao `AGENTS.md` (e ao `CLAUDE.md`,
com o caminho `.claude/skills`), criando o arquivo se necessário, para que
prompts como “adicione um teste para o checkout” usem a skill automaticamente.
Se você instalar a skill de outra forma, adicione esta linha você mesmo:

```md title="AGENTS.md"
End-to-end tests use e2e; read .agents/skills/e2e/SKILL.md before writing or running one.
```

O pacote `e2e` também inclui esta documentação offline, em
`node_modules/e2e/docs/`, para que os agentes a leiam localmente.

<Accordion title="Instale o plugin para Claude Code, Codex ou Cursor">

O repositório do e2e é um marketplace de plugins para Claude Code e Codex, e
para o Grok Build, que lê os arquivos do Claude Code. O Cursor carrega o plugin
da sua pasta de plugins locais:

<CodeGroup>
```bash Claude
claude plugin marketplace add e2e-inc/e2e
claude plugin install e2e@e2e
```

```bash Codex
codex plugin marketplace add e2e-inc/e2e
codex plugin add e2e@e2e
```

```bash Cursor
repo=$(mktemp -d)
git clone --depth 1 https://github.com/e2e-inc/e2e "$repo"
mkdir -p ~/.cursor/plugins/local
rm -rf ~/.cursor/plugins/local/e2e
cp -R "$repo/plugins/e2e" ~/.cursor/plugins/local/
```
</CodeGroup>

Inicie uma nova sessão. No Cursor, rode **Developer: Reload Window**. No Cursor
Teams e Enterprise, plugins locais precisam da configuração de administrador
**Allow Local Plugin Imports**, ou um administrador importa `e2e-inc/e2e` como
marketplace da equipe. O plugin adiciona as skills
`e2e`, `create-verification-skill` e `migrate-to-e2e`, não o pacote npm. No
Codex e no Cursor, ele também adiciona o [servidor MCP](/mcp-server); no Claude
Code e no Grok Build, registre o servidor no projeto. Invoque as outras duas sob
o nome do plugin, `/e2e:<skill>` no Claude Code e `$e2e:<skill>` no Codex, e como
`/<skill>` no Cursor.

A versão do plugin acompanha os lançamentos do e2e. Para atualizá-lo, rode
estes comandos e inicie uma nova sessão. No Cursor, rode de novo os comandos
acima.

<CodeGroup>
```bash Claude
claude plugin marketplace update e2e
claude plugin update e2e@e2e
```

```bash Codex
codex plugin marketplace upgrade e2e
```
</CodeGroup>

</Accordion>

<Accordion title="Deixe o pnpm criar o link da skill">

O pnpm 12.11 ou posterior pode criar um link para a skill a partir do pacote
`e2e` instalado, em vez da cópia que o `init` escreve. Até você escolher, todo
`pnpm install` lista `e2e skills` como aguardando aprovação. Escolha no
`pnpm-workspace.yaml` da raiz do workspace, onde o pnpm cria os links das
skills:

- **Mantenha a cópia.** Defina `skills: false`. A linha de aprovação some.
- **Deixe o pnpm criar o link.** Use o pnpm 12.18 ou posterior: versões
  anteriores chamam o link de `pnpm-e2e-e2e`, não de `e2e`, o nome que o
  `AGENTS.md` usa. Apague `.agents/skills/e2e` e `.claude/skills/e2e` e depois
  defina `skills: true` ou rode `pnpm approve`. Cada instalação cria o link da
  skill nas pastas de skills da raiz e adiciona o link ao `.gitignore` dessas
  pastas, então a skill acompanha cada atualização do `e2e`. Antes da primeira
  instalação, a skill não existe: um agente que lê um clone novo não encontra
  nada nesse caminho.

```yaml title="pnpm-workspace.yaml"
permissions:
  e2e:
    skills: true
```

Quando ainda existe uma cópia, o pnpm cria o link da skill ao lado dela, com o
nome `pnpm-e2e-e2e`, e os agentes carregam duas skills `e2e`. O `init` e o
`upgrade` avisam sobre isso: apague a cópia e depois rode `pnpm install --force`
para renomear o link para `e2e`. Nenhum dos dois comandos sobrescreve o link do
pnpm, e o `init` não adiciona uma cópia onde o pnpm cria o link da skill,
inclusive em um membro do workspace.

</Accordion>

## Deixe o agente usar o app

O `e2e mcp` dá ao agente uma sessão ao vivo no seu app. O agente confere seus
localizadores na tela antes de escrevê-los e verifica as próprias mudanças na
UI. O `init` registra o servidor. Veja [Servidor MCP](/mcp-server) para
configuração e prompts.

## Como um agente escreve e roda um teste

A skill instrui o seu agente a ler primeiro a sua configuração e um teste
existente. Com o `e2e mcp`, ele percorre o fluxo em uma sessão ao vivo e
escreve cada passo à medida que avança. Cada teste verifica um comportamento:
prepare o estado inicial, aja rumo a um objetivo e, no fim, verifique o
resultado:

```ts title="tests/shop.e2e.ts"
import { test, expect } from 'e2e';

test('filters the shop to items under $20', { session: 'customer' }, async ({ app, agent, screen }) => {
  const results = screen.getByRole('status', 'Results');
  const products = screen.getByRole('list', 'Products').getByRole('listitem');
  await app.open('/shop');
  await results.waitFor();
  await products.filter({ hasText: 'Leather Backpack, $90' }).waitFor();

  await agent.act('show only items under $20');

  await expect(results).toHaveText('2 items under $20');
  await expect(products).toHaveText(['Canvas Tote, $14', 'Steel Bottle, $18']);
});
```

- **Um comportamento e um [objetivo](/core-concepts#goals) por teste.** Dê ao
  `agent.act` os passos específicos de que ele precisa para alcançar esse
  objetivo. Divida o caminho em várias chamadas quando um passo posterior
  precisar de um estado de tela conhecido, quando um fluxo longo arriscar
  estourar os orçamentos `maxSteps` ou `maxModelCalls`, ou quando uma falha no
  meio precisar de uma fronteira de passo própria. Explique a divisão e espere
  pelo estado de tela intermediário antes de continuar. Confira o resultado no
  fim para verificar o comportamento e confirmar a
  [gravação](/cache#when-a-recording-is-written).
- **Localizadores nomeados.** Um localizador que o teste usa duas vezes, como
  `results`, vira uma `const`, então renomear um controle exige uma única
  edição.
- **Sem sleeps.** Os localizadores fazem polling, as ações esperam pelo
  elemento-alvo e o `expect` tenta novamente até o seu tempo limite.
- **Dê a cada usuário uma sessão separada.** Um
  [teste de preparação](/authentication) faz login com
  `credentials.user(name)` e salva a sessão do usuário principal. Para um fluxo
  como um chat, [abra uma segunda sessão](/core#open-a-host-inside-a-test) e
  verifique o resultado na sessão do destinatário. Nunca escreva uma senha ou
  outro segredo em um teste: declare as credenciais do runner na configuração e
  passe os segredos de um segundo host por `launch({ secrets })`.

Enquanto itera, o agente roda só o teste que está editando (pelo número da
linha) com `--action-timeout 5000`, para que um localizador errado falhe em 5
segundos em vez de 30:

<CodeGroup>
```bash npm
npx e2e run tests/checkout.e2e.ts:3 --action-timeout 5000
```

```bash pnpm
pnpm exec e2e run tests/checkout.e2e.ts:3 --action-timeout 5000
```

```bash bun
bunx e2e run tests/checkout.e2e.ts:3 --action-timeout 5000
```
</CodeGroup>

O agente deixa o cache de replay ligado, para que os objetivos que passam sejam
reproduzidos sem chamar um modelo, e desliga as novas tentativas (já que elas
rodam todos os objetivos ao vivo). Quando o teste passa, o agente remove
`--action-timeout` e roda o teste uma vez com `--no-cache` para garantir que o
agente ao vivo ainda conclua todos os objetivos. Veja
[Rode um teste de novo enquanto o corrige](/cache#rerun-a-test-while-you-fix-it).

## Como um agente lê uma falha

Por padrão ([`trace`](/reference/config#trace)), o e2e escreve um arquivo
`trace.md` em `.e2e/results/` para cada teste que falhou, excedeu o tempo
limite, foi interrompido ou se mostrou instável. O terminal imprime o caminho
logo abaixo da falha (`❯ trace .e2e/results/<test>/trace.md`).

O seu agente de código lê o `trace.md` em vez do `report.json` bruto. O arquivo
inclui a linha que falhou, o alvo e o resultado de cada passo, erros do
console, requisições de rede que falharam, os últimos turnos do agente e a tela
no momento da falha. Se o agente precisar conferir uma tela que não está no
trace, ele abre a URL dessa tela diretamente em uma sessão MCP, em vez de
percorrer o fluxo de novo desde o início.

Para inspecionar chamadas ao modelo uma a uma, passe `--ai-trace --no-cache` e
leia a saída com o [unbox-ai](/debugging#agent-steps). Não cole o
`ai-trace.json` bruto no contexto de um agente, já que o arquivo repete prompts
entre turnos e pode chegar a vários megabytes.

## Gere uma skill de verificação para o seu app

A skill `e2e` ensina o framework, não o seu app. A skill
`create-verification-skill` gera uma skill local do projeto,
`.agents/skills/verify-<app>/`, feita sob medida para o seu app, e a testa uma
vez antes de terminar.

<CodeGroup>
```bash npm
npx skills add e2e-inc/e2e --skill create-verification-skill
```

```bash pnpm
pnpm dlx skills add e2e-inc/e2e --skill create-verification-skill
```

```bash bun
bunx skills add e2e-inc/e2e --skill create-verification-skill
```
</CodeGroup>

Depois, peça ao agente `/create-verification-skill`.

<Accordion title="O que a skill gerada contém">
- Comandos de inicialização e de doctor a partir da sua configuração.
- As duas formas de controlar o app: uma sessão ao vivo do `e2e mcp` e um
  teste.
- As evidências que uma prova guarda.
- Um mapa de funcionalidades com um charter de `e2e explore` para cada
  funcionalidade, para que um [bug bash](/bug-bash) se distribua a partir do
  mapa.

A skill gerada diz só o que é verdade sobre o seu app e aponta para a skill do
e2e para o resto. Ela é baseada na
[create-verification-skill](https://github.com/cursor/plugins/tree/main/pstack/skills/create-verification-skill)
do pstack de poteto, com o e2e no lugar de um harness feito à mão.
</Accordion>

## Migre uma suíte existente

A skill `migrate-to-e2e` move uma suíte de Playwright, Cypress, Selenium,
Appium, Detox, Maestro ou TesterArmy para o e2e, uma fatia por sessão. A suíte
antiga continua rodando ao lado dos novos testes, então você pode parar depois
de qualquer sessão.

<CodeGroup>
```bash npm
npx skills add e2e-inc/e2e --skill migrate-to-e2e
```

```bash pnpm
pnpm dlx skills add e2e-inc/e2e --skill migrate-to-e2e
```

```bash bun
bunx skills add e2e-inc/e2e --skill migrate-to-e2e
```
</CodeGroup>

Depois, peça ao agente `/migrate-to-e2e`. Ele porta a fatia que você escolher
e roda cada teste portado três vezes em cada alvo. Um arquivo `MIGRATION.md`
registra o progresso para a próxima sessão. Opcionalmente, o agente planta um
bug temporário no app, como um total errado no checkout, e verifica se as duas
suítes falham com ele. O agente só apaga um teste antigo quando você confirma.
Primeiro, ele lê o guia de migração do seu runner:
[Playwright](/migrate/playwright), [Cypress](/migrate/cypress),
[Selenium](/migrate/selenium), [Appium](/migrate/appium), [Detox](/migrate/detox),
[Maestro](/migrate/maestro) ou [TesterArmy](/migrate/testerarmy).
