O e2e funciona em qualquer serviço de CI que rode Node 24.8+ (22.22.3+ no
Node 22), ou [Bun](/reference/cli#bun) 1.4.3+ para testes web. Um job típico
instala as dependências, inicia o app ou o dispositivo, roda `e2e run` e faz
upload de `.e2e/`.

## Faça upload dos relatórios

Sempre faça upload de `.e2e/` no fim de um job, mesmo quando os testes falham:

| Caminho | O que tem dentro |
| --- | --- |
| `report.json` | Relatório JSON completo da execução |
| `junit.xml` | JUnit XML (com `--reporter list,junit`), incluindo os testes filtrados, marcados como pulados, e as falhas de inicialização |
| `results/` | Páginas de trace, capturas de tela, dumps de tela e vídeos (com `--video`) |

Aponte a visualização de relatórios de teste do seu serviço de CI para
`.e2e/junit.xml`. No GitLab, o `junit.xml` vincula automaticamente as capturas
de tela das falhas, que aparecem no próprio relatório. Você pode mudar o local
de `.e2e/` com a opção [`output`](/reference/config#output).

## Credenciais do modelo

Passe a chave de API que o seu provedor espera, como `AI_GATEWAY_API_KEY` (veja
[Modelos](/models)). Suítes só com localizadores não precisam de nenhuma chave
de modelo.

<Warning>
Todo job com uma chave de API a expõe ao código dos seus testes, à configuração
e às dependências. Dê segredos apenas a branches em que você confia. Rode o
código de pull requests não confiáveis sem segredos e sem tokens de escrita.
Veja [Segurança](/security).
</Warning>

Guarde as chaves nos segredos da CI e defina limites de gastos onde o seu
provedor permitir. O GitHub Actions automaticamente não repassa os segredos a
pull requests vindos de forks.

## O que muda na CI

O modo CI é ativado sempre que a variável de ambiente `CI` tem qualquer valor
diferente de vazio, `0` ou `false`. Para testar o comportamento da CI
localmente, rode `CI=1 npx e2e run`:

| Configuração | Local | CI |
| --- | --- | --- |
| `retries` | `0` | `1` |
| `workers` | metade dos seus núcleos | `1` |
| `cache` quando não definido | `read-write` | `read-only` |
| `.only` | permitido | faz a execução falhar |
| `command.reuseExisting` | respeitado | ignorado |

Para mudar os padrões de workers e de novas tentativas, use flags:

<CodeGroup>
```bash npm
npx e2e run --workers 4 --retries 0
```

```bash pnpm
pnpm exec e2e run --workers 4 --retries 0
```

```bash bun
bunx e2e run --workers 4 --retries 0
```
</CodeGroup>

Para não enviar [telemetria](/telemetry#in-ci) da CI, adicione
`E2E_TELEMETRY_DISABLED: '1'` ao `env` do job.

## Jobs mobile

Sem um [serviço de dispositivos hospedados](/mobile#hosted-devices), cada
plataforma precisa de máquina, build e dispositivo próprios:

| | iOS | Android |
| --- | --- | --- |
| Máquina | macOS com Xcode e um runtime de simulador | Linux com KVM (virtualização aninhada) |
| Build | `.app` Release para simulador, sem assinatura de código | `.apk` Release |
| Dispositivo | Um simulador inicializado | Um emulador inicializado |

Faça um build Release nas duas plataformas. Um build de debug de React Native
ou Expo carrega o JavaScript do Metro, que esses jobs não iniciam, então ele
abre em uma tela de erro. Os exemplos usam um projeto React Native com `ios/`
e `android/` no repositório. Para um projeto Expo sem essas pastas, rode
`npx expo prebuild` antes.

Instale o build e depois rode a suíte:

<CodeGroup>
```bash npm
# iOS
xcrun simctl install booted path/to/MyApp.app
npx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
npx e2e run --target android --reporter list,junit
```

```bash pnpm
# iOS
xcrun simctl install booted path/to/MyApp.app
pnpm exec e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
pnpm exec e2e run --target android --reporter list,junit
```

```bash bun
# iOS
xcrun simctl install booted path/to/MyApp.app
bunx e2e run --target ios --reporter list,junit

# Android
adb install -r path/to/app.apk
bunx e2e run --target android --reporter list,junit
```
</CodeGroup>

Os comandos supõem dois alvos chamados `ios` e `android`, cada um com uma
engine `mobile()` e o `bundleId` do app. Veja
[Aponte para o seu app](/mobile#point-at-your-app). Para deixar a suíte
instalar o build, defina `app.appPath` e chame `device.installApp()`.

Estas regras valem em todo serviço:

- **Um job para cada plataforma.** Rode `--target ios` em um Mac e
  `--target android` no Linux com KVM. Os Macs hospedados usam Apple Silicon,
  que não consegue aninhar virtualização, então o emulador Android não inicia
  neles.
- **Faça o boot do dispositivo em um step próprio.** Sem nenhum
  dispositivo inicializado, a engine pede ao agent-device que faça o boot
  de um, mas um runner Linux novo não tem imagem de emulador. Um step
  separado também diferencia um boot que falhou de um teste que falhou.
- **Fixe o runtime do iOS.** Um simulador escolhido pelo nome (`iPhone 17`)
  roda o iOS padrão da imagem, e a árvore de acessibilidade muda entre
  versões do iOS. Uma atualização da imagem do runner pode então fazer uma
  asserção de localizador falhar sem nenhuma mudança no seu código. Os
  exemplos criam um simulador em um runtime indicado pelo nome e fazem o
  boot dele pelo UDID. Substitua `iOS-26-5` por um runtime que a imagem
  tenha (`xcrun simctl list runtimes`).
- **Faça cache de `~/.agent-device/apple-runner/derived`.** O agent-device
  faz o build do runner XCUITest dele ali na primeira vez que controla um
  simulador. Não faça cache de todo o `~/.agent-device`. O resto é o estado
  do último daemon, e uma cópia restaurada pode interromper a próxima
  execução com `Failed to communicate with daemon`.
- **Reproduza gravações locais.** A chave do cache de replay inclui o app,
  não o dispositivo, então um passo gravado no seu simulador é reproduzido no
  simulador da CI.
  [Faça commit do cache de replay](/cache#commit-the-replay-cache).

## Bloqueie o merge de pull requests

Todo código de saída diferente de zero faz o job falhar, inclusive passos do
agente que falharam. Torne o job do e2e uma verificação obrigatória para
bloquear merges quando houver falhas; não dependa só da contagem de testes que
falharam em um arquivo de relatório, já que ela não vê erros no nível da
execução. Veja os códigos de saída em
[Depurar uma execução](/debugging#read-the-failure).

Para manter as verificações de PR rápidas e previsíveis:

- Dê a cada `agent.act` os passos rumo a um [objetivo](/core-concepts#goals)
  e coloque depois de cada chamada uma asserção de localizador ou um
  `agent.assert`.
- [Faça commit do cache de replay](/cache#commit-the-replay-cache) para que os
  passos `agent.act` gravados sejam reproduzidos sem nenhuma chamada ao
  modelo. (Cache misses, devoluções do controle ao agente e julgamentos do
  agente ainda chamam o modelo.)
- Fique de olho em testes instáveis: o e2e marca como instável todo teste que
  só passa em uma nova tentativa.
- Use `--max-failures <n>` para encerrar cedo diante de um deploy quebrado, em
  vez de gastar chamadas ao modelo em cada teste restante.
- Use `--max-duration <ms>` para limitar o tempo de execução dos testes (o
  cronômetro dispara quando os testes começam, sem contar a inicialização do
  app).

## Rode só os testes afetados

Passe `--changed-since` em pull requests para que um
[filtro de testes](/filters) pule os testes que o diff provavelmente não afeta
e rode primeiro os arquivos de maior risco. Sem a flag (como na `main`), a
suíte inteira roda. Veja
[Adicione o filtro de decisão](/filters#add-the-decision-filter).

## Faça cache do histórico de tempos

Ao rodar com vários workers, o `e2e run` usa `<output>/timings.json`
(`.e2e/timings.json` por padrão) para começar pelos arquivos de teste mais
lentos. Salve e restaure esse arquivo no cache da sua CI para que checkouts
novos mantenham o ganho de velocidade. Veja um exemplo em
[GitHub Actions](/ci/github-actions#cache-the-timings-history).

- O arquivo serve só de orientação: um arquivo ausente ou inválido nunca afeta
  os resultados dos testes.
- Execuções parciais (`--grep`, `--last-failed`) não sobrescrevem os tempos
  dos arquivos que não rodaram por inteiro.
- Use a branch como chave do cache, com a `main` como alternativa (e inclua o
  índice do shard se você usar [sharding](#sharding)).
- Lembre-se de que a CI usa `workers: 1` por padrão; defina `workers` ou passe
  `--workers` para paralelizar.

## Sharding

Passe `--shard <index/total>` para dividir uma suíte entre jobs de CI
paralelos. Toda máquina fatia a suíte de forma determinística. Se um shard
puder ficar sem nenhum teste (por exemplo, com uma matriz maior que a suíte),
adicione `--pass-with-no-tests`. Veja os detalhes da divisão na
[referência da CLI](/reference/cli#flags).

No GitHub Actions, uma matriz roda um job para cada shard:

```yaml
jobs:
  e2e:
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3]
    steps:
      # ...
      - run: npx e2e run --shard ${{ matrix.shard }}/3 --pass-with-no-tests --output .e2e/shard-${{ matrix.shard }}
```

Para rodar de novo as falhas de um shard antes do upload, use
`e2e run --last-failed` com o `--output` original desse shard. Omita `--shard`
para que a reexecução use as falhas já selecionadas desse shard.

Use um job final para publicar um único relatório para a matriz:

1. Faça upload do diretório de saída de cada shard com `if: always()`. Inclua
   `report.json`, `report-with-reruns.json` quando existir, e `results/`.
2. Dê ao job de mesclagem `needs: e2e` e `if: always()`. Faça checkout da
   mesma revisão, instale o projeto e baixe os artefatos desta execução e
   desta tentativa do workflow em diretórios separados, como `.e2e/shard-1`,
   `.e2e/shard-2` e `.e2e/shard-3`.
3. Rode [`e2e merge-reports`](/reference/cli#e2e-merge-reports) nesses
   diretórios. Todo shard precisa estar presente, inclusive os vazios. Faça
   upload do diretório mesclado inteiro com `if: always()` para manter os
   links de trace funcionando.

<CodeGroup>
```bash npm
npx e2e merge-reports .e2e/shard-* --output .e2e/merged --reporter junit,markdown
```

```bash pnpm
pnpm exec e2e merge-reports .e2e/shard-* --output .e2e/merged --reporter junit,markdown
```

```bash bun
bunx e2e merge-reports .e2e/shard-* --output .e2e/merged --reporter junit,markdown
```
</CodeGroup>

Configure os reporters que publicam no PR, como `github()`, só no job de
mesclagem, por exemplo passando um `--config` separado nele. Dê a esse job as
permissões de que o reporter precisa. Se você mantiver a configuração de
mesclagem em um subdiretório, passe um caminho absoluto em `--output` para
colocar o relatório fora desse diretório. Para rodar de novo as falhas da
matriz inteira, baixe o diretório mesclado e, no comando que roda os testes,
passe `--last-failed --output` com o caminho desse diretório.

## Reexecutando falhas

`--last-failed` roda de novo só os testes que falharam na execução anterior
(lidos de `.e2e/report.json`). Você pode encadeá-lo no mesmo step da CI:

```yaml
      - run: npx e2e run || npx e2e run --last-failed
```

A reexecução mantém os artefatos originais, salva os seus em `rerun-<n>/` e
escreve um `report-with-reruns.json` combinado ao lado do `report.json`. Se
você rodar a reexecução em um job de CI separado, baixe o `report.json` do
job anterior (mais o `report-with-reruns.json` e `results/` se quiser o
histórico completo).
